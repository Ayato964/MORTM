# 質問状：この比較実験は本当に「公平」でしょうか？
### — 記号音楽（MIDI）基盤モデルにおけるトークン化／学習スキームの比較について —

**作成日:** 2026-06-24
**読者:** このプロジェクトを知らない外部の専門家・査読者
**お願い:** 以下の実験設計が「公平な比較」として成立しているか、率直なご判断をいただきたい。私自身が公平性に疑問を持っている点（§5）を特に見ていただきたい。

---

## 1. 背景：何を主張したい論文か

記号音楽（MIDI）の基盤モデルを作っている。MIDIをTransformerに入れるには音楽イベントを離散トークン列に変換する必要がある。**「私たちの提案する学習用トークン化スキームは、素朴な（REMI型の）スキームより、基盤モデルとして下流タスクで優れているか」** を実証したい。

トークン化が違うと同じ楽曲でもトークン列の長さが変わるため、単純な比較ができない（per-tokenの損失は比較不能）。そこで **「楽曲集合を固定し、スケーリング則で各条件を compute-optimal なモデルサイズに最適化してから、トークン化に依存しない下流指標で比較する」** という設計を採った。

---

## 2. 比較する2条件の正確な定義（重要）

両条件は **全く同じトークン語彙（約647語）** を使う。違うのは**学習サンプルの作り方**だけである。

- **条件P（提案）：** 楽曲を「過去/中央/未来」の3ブロックに区切り、学習サンプルごとに **ブロックをランダムに並び替え・削除（3ブロック中0〜2個を一様にランダム削除）** する拡張を施す。任意のブロック配置から予測を学ぶ（基盤モデルの柔軟性・補完能力を狙う）。
- **条件R（ベースライン、REMI相当）：** 同じトークンだが **ブロックの並び替え・削除をしない**（固定順の線形系列）。これを「素朴なREMI型」とみなしている。

> **率直な前置き：** したがって本実験は厳密には「2つの独立したトークナイザの比較」ではなく、**「同一語彙の下で、ブロック並び替え・削除という学習スキーム（データ拡張）の有無を比較」** している。条件Rは独立に設計されたREMIではなく「提案からブロック操作を除いたもの」である。この点が公平性の論点になりうる（§5-A）。

## 3. 公平性のために固定した条件

| 固定した不変量 | 値 |
|---|---|
| 楽曲集合 | **共通 130,500 ユニーク原曲**（×12転調 = 1,566,000 サンプル、両条件で完全に同一の楽曲） |
| tokens/parameter 比 r\* | **200**（両条件共通。スケーリング則の compute-optimal 比から） |
| 最適化器・学習率則・エポック方針 | 共通 |
| グローバル有効バッチ | 1024 系列/step（共通） |

## 4. 各条件で「自然に」変わった量

| | 条件P（提案） | 条件R（REMI相当） | 比 P/R |
|---|---|---|---|
| 学習トークン数 D | 6.91 B | 10.33 B | **0.669** |
| モデルサイズ N（= D/200 で導出） | 60.5 M | 86.0 M | 0.703 |
| 計算量 C（≈6ND） | 2.4e18 | 5.3e18 | **0.47** |
| tokens/parameter（= D/N） | **120** | **120** | 1.00 |
| 学習後 val loss（参考・比較不可） | 1.382 | 1.371 | — |

設計の意図：
- モデルサイズ N は各条件の D から **N=D/r\*** で導出（Chinchilla 流の compute-optimal サイジング）。両条件に**同じ r\*=200** を当てた。
- 結果として **tokens/parameter は両条件とも 120 で完全一致**（＝両モデルが同じ密度で学習される）。
- 計算量は条件Pが条件Rの **約47%**。これを「効率」の主張軸（パレート比較：少ない計算で同等以上）に使う予定。
- 補助として **条件C（提案を条件Rと同じ計算量＝126.5Mにした点）** も学習済みで、「同計算量でも提案が優れる」を別途確認する二段構え。

## 5. 私が公平性に疑問を持っている点（ぜひご判断ください）

### 5-A. これは「トークン化の比較」か「データ拡張の比較」か？
両条件は同一語彙で、違いはブロック並び替え・削除の有無のみ。これを「提案トークン化 vs REMI」と呼ぶのは妥当か。それとも「ブロック拡張あり/なし」と正直に書くべきか。条件Rを本当の独立REMI実装にしないと「既存手法に勝った」とは言えないのではないか。

### 5-B. トークン数の差は「圧縮効率」ではなく「ブロック削除」由来
条件Pのトークン数が少ない（D比0.669）のは、**ブロック削除（平均で3個中1個＝1/3を削除）**が原因である（期待値 1−1/3=0.667 が実測0.669とほぼ一致）。**両条件のイベント当たりの符号化は完全に同一**で、圧縮効率の差ではない。
- すると「提案は同じ音楽を少ないトークンで表せる（=効率的）」という効率主張は成り立つのか？ 実態は「提案は学習時に内容の一部を削除した版を見ている」だけではないか。
- 一方で、削除は提案手法の学習スキームの本質（任意部分からの予測を学ぶ）でもある。この場合、何を「効率」と呼ぶのが正当か。

### 5-C. モデルサイズ N が違う（60.5M vs 86.0M）
compute-optimal を理由に提案へ**小さいモデル**を与えている。「もし提案にも86Mを与えたらさらに良くなるのでは」という反論に、条件C（提案126.5M＝同計算量）で十分応えられているか。

### 5-D. 計算量が違う（提案は47%）
提案が**少ない計算量**で学習する。もし提案が下流で勝てば「効率の良さ」の強い証拠になる（少計算で勝つ）。だが負けた場合の解釈は曖昧。この非対称性を踏まえ、主張をどう限定すべきか。

### 5-E. 過剰パラメータ（両条件 約1.7倍）
N は full-corpus 基準で決めたため、130,500曲の subset に対しては両条件とも約1.7倍の過剰パラメータ（compute-optimal は提案35M/REMI52M）。両条件同率なので相殺されると考えているが、これは許容されるか。subset-optimal に揃えるべきか。

## 6. 下流評価（参考）

token perplexity は比較不能なので使わない。**生成・補完・分析の3タスクで両モデルを同条件で SFT し、トークン化に不変な指標（音符レベルの分布距離・補完の音符F1・分類精度、必要なら bits-per-note）で比較**する予定。
