## 1. 研究の問い

**「提案する記号音楽（MIDI）トークン化手法は、既存手法より、基盤モデルとして下流タスクで高い精度を出すか？」**

トークナイザは同じ楽曲でも生成するトークン列の長さ・語彙が異なるため、公平な比較が難しい（per-token perplexity は比較不能、fertency=冗長度の交絡）。本研究は **スケーリング則で各手法を compute-optimal に最適化してから比較する** という新しい評価パラダイムを採る。設計の妥当性は別途専門家レビューで支持されている（添付 PROPOSAL 参照）。

---

## 2. 比較する2つのトークン化

| | 提案手法 | ベースライン（≈REMI） |
|---|---|---|
| 中身 | REMI系（小節`<SME>`/位置`s_`/音高`p_`/長さ`d_`）＋**ブロック構造**（PAST/CONST/FUTURE 区間）＋**ブロックの並び替え・削除**による拡張 | 同じ語彙だが**ブロック移動なし**（線形固定順）。実質 REMI |
| 語彙 | 約647（vocab_size=700） | 同じ |
| 性格 | 任意のブロック配置から予測を学ぶ柔軟性（基盤モデル向け） | 標準的な線形系列 |

両者は同一トークナイザ語彙で、違いは **「ブロックの並び替え・削除という拡張の有無」**。これを `disable_block_augment` フラグで切替（`mortm/utils/convert_foundation.py`）。

## 3. 公平性の設計（確定）

### 固定する不変量
- **楽曲集合：共通 130,500 ユニーク原曲**（×12転調 = 1,566,000 サンプル、両アーム完全同一）
- **最適 tokens/parameter 比 r\*=200**（両アーム共通。理由は §5）
- 最適化器・LR則・エポック方針

### 各トークナイザで自然に変わる量（これがトークナイザの「効率」を反映）
| アーム | 学習トークン D | モデルサイズ N | 計算量 C |
|---|---|---|---|
| 提案 | 6.91B | 60.5M | 2.4e18 |
| REMI | 10.33B | 86.0M | 5.3e18 |

- N は **N = D/r\*** で各アームの D から導出（Chinchilla 流の compute-optimal サイズ決定、ラグランジュ未定乗数法 αA·N^−α=βB·D^−β の解）。
- **N比 = D比 = 0.669**（提案の圧縮効率をそのまま反映）。
- **tokens/param は両アームとも 120 で完全一致**（D_train/N = 200·S/全曲数、トークナイザに依存しない）。＝両モデルが同じ密度で学習される＝過小/過剰学習バイアスが無い。

### 主張の二段構え（パレート比較）
1. **効率**：提案は REMI の **約45%の計算量**で同等以上 → 「圧縮効率の高いトークナイザは小さく安いモデルで足りる」
2. **絶対性能**：別途 **C点（提案を REMI と同FLOPs=同計算量にした 126.5M モデル）** を用意し、同計算量でも提案が上回ることを確認

### 学習する3モデル（「珠玉3点」）
| | トークナイザ | N | D | LR | 役割 |
|---|---|---|---|---|---|
| A | 提案 | 60.5M | 6.91B | 1.3e-3 | content-equivalent（効率主張） |
| B | REMI | 86.0M | 10.33B | 1.2e-3 | content-equivalent（基準） |
| C | 提案 | 126.5M | 6.91B | 9e-4 | compute-equivalent to B（絶対性能主張） |

全モデル：縦横比 d/L≈70（深さアブレーションの最適帯）、head_dim=64、SwiGLU、RMSNorm、RoPE。グローバル有効バッチ=1024系列/step。

## 4. 下流タスクと評価（PPL非依存）

トークン化に**不変な内容空間の指標**のみ使用（token perplexity は使わない）。提案では **生成・補完・分析の3タスクで SFT** し評価する方針：
- **生成**：デコード後の音符レベル分布（pitch-class・rhythm density の参照との一致）、リスニング
- **補完（infilling）**：参照との音符レベル F1/一致（音楽時間で照合）
- **分析**：分類精度/F1（本質的にトークン非依存）
- 尤度を使う場合は **bits-per-note**（bits-per-byte の音楽版）に正規化

SFT は A/B 各アームで同一データ・同一ステップに揃える。

## 5. スケーリング則の根拠（既測定）

提案・REMI 両トークン化で 5サイズ×5データ=各25点の格子を測定済み。
- 形：`L(N,D) = E + A·N^−α + B·D^−β`、既約損失 E ≈ 1.0–1.2 nats
- **β（データ指数）≈ 0.7–0.9**（測定可能、LLM の約2–3倍急峻＝MIDIは低エントロピー）
- **α（モデル指数）は同定不能**（損失地図が「平らな谷」、α∈[0.25,1.0]で損失ほぼ不変）
- **compute最適 tokens/param ≫ 20**（Chinchilla の一桁上、実測で60–420）→ r\*=200 を採用

> **方法論上の注意（査読対応）：** N を決める r\* は α に依存し、その α が同定不能。これを「弱点」ではなく「IsoFLOP の平坦性により N\* がブレても下流性能ペナルティは小さい（頑健）」「両アームに同一 r\* を当てるため選択バイアスが相殺される」と正当化する。

## 6. 現在の進捗と「重大な問題と修正」（透明性のため記載）

### 進捗（2026-06-24 更新）
- データセット構築完了（共通130,500曲、提案6.91B / REMI10.33B、リーク無し検証済）。
- モデルconfig 3点・学習ランナー構築完了。
- **基盤モデル3点の学習完了（下表）。** 各モデルは保存時に損失値が付与され（未学習の_0.0ではない）、A は eval cross-entropy=1.27（未学習初期値6.7と明確に異なる）で学習を再検証済み。

| モデル | N | 最終 val loss | 備考 |
|---|---|---|---|
| A 提案 | 60.5M | 1.382 | eval CE実測1.27で学習確認 |
| B REMI | 86.0M | 1.371 | |
| C 提案(compute-eq) | 126.5M | 1.300 | |

※ 提案(v5 eval)と REMI(no-aug eval)は eval 系列分布が異なるため **loss 絶対値は直接比較不可**。比較は下流タスク（§4）で行う。
- **次段階：下流3タスク（生成・補完・分析）の SFT データ・評価器を構築し、A/B/C を同条件で SFT → トークン非依存指標で比較。**

### 発見・修正したバグ（重要）
最初の学習試行で **モデルが全く学習しない**（loss=0.0、保存モデルの eval cross-entropy=6.71 が未学習初期値6.72と同一）事象が発生。原因を以下と特定し修正済み：

- **原因：** 学習コードの損失マスク（`loss_mask`）が、`<MGEN>/<CGEN>/<META>` という**生成マーカートークン出現後のトークンのみ**損失計算する実装だった（これは指示型 downstream SFT 用の仕様）。本研究の foundation 事前学習データ（ブロック構造 SYSTEM/PAST/CONST/FUTURE）は**これらのマーカーを含まない**（実測 0/344 系列）ため、**損失マスクが全て 0 → 損失 0 → 勾配 0 → 未学習**となっていた。
- **検証：** 保存モデルをロードし eval データで実 cross-entropy を測定（6.71）、未学習初期値（6.72）と一致＝全く学習していないことを確認。
- **修正：** マーカーを含まない系列（=foundation データ）は**全トークンで損失を計算**するよう `loss_mask` を変更。マーカーを持つ系列（downstream SFT）は従来通り。修正後、短時間テストで損失が 6.63 から減少することを確認し、本学習を再開。
- **教訓/留意：** スケーリング則の測定（25点格子）は当時の別バージョンのパッケージ（全トークン損失）で実施されており、その結果は有効。今回の foundation 学習はパッケージ更新後に上記マスクが混入していた。スケーリング結果と本実験の損失レジームは整合する。

## 7. 専門家にお聞きしたい点

1. **公平性の妥当性**：「共通楽曲＋共通 r\*＋tokens/param一致、計算量差はパレート主張」という設計で、トークン化比較として十分公平か。compute-equivalent 点（C）の追加で「同計算量でも優位」を示せば反論を封じられるか。
2. **下流評価**：生成・補完・分析の3タスク SFT ＋ bits-per-note という構成で、トークン化の質を測るのに十分か。他に必須の指標はあるか。
3. **r\* の扱い**：α 同定不能下で共通 r\*=200 を採る正当化（IsoFLOP平坦性＋選択バイアス相殺）は査読に耐えるか。r\* の感度分析をどこまで示すべきか。
4. **過剰パラメータ**：130,500曲に対し N は full-corpus 基準（提案60.5M/REMI86.0M、subset に対しては約1.7倍の過剰パラメータ、両アーム同率）。これは許容されるか、subset-optimal（提案35M/REMI52M）に揃えるべきか。
